# ARTEX 改进规划

## 资产同步

- 记录日期：2026-10-10
- 状态：待实施
- 当前决定：先记录规划，不修改同步代码、不部署同步功能变更。
- 目标：让用户明确知道同步了什么、是否完整、哪些数据失败，并能在刷新页面后回看结果。

### 当前情况

1. 任务维度列表中的 `100%` 来自 ScopeSentry 扫描任务进度，不能用于判断 ARTEX 资产同步是否完成。
2. 同步结果仅保存在当前页面状态中。数量位于列表分页按钮下方，错误和警告仅在发生时显示；刷新或离开页面后，结果无法回看。
3. 同步接口返回后，页面统一提示“同步完成”，即使返回结果包含错误或截断警告，也可能让用户误以为全部成功。
4. 当前每个所选任务、每种资产类型最多拉取 5000 条；达到上限便停止拉取并标记截断，没有核验是否确实还有剩余数据。
5. 当前同步子域名、服务、App，以及从子域名记录派生的关联 IP，只映射部分字段，不会完整复制源平台的所有扫描数据。
6. 部分缺少关键字段的资产会直接跳过，部分关联 IP 写入失败没有反馈；现有数量按成功写入操作累计，不能直接理解为新增或独立资产数量。

实现参考：[同步后端](../server/sync_scopesentry.go)、[同步页面](../web/src/app/(main)/function/sync/page.tsx)。

### 实施顺序

第一阶段优先实施 AS-01 至 AS-04：先完善同步结果模型与反馈，再保存历史并展示状态，解决“是否同步成功、是否完整”的判断问题。

第二阶段实施 AS-05、AS-06：完善大批量同步、断点恢复、字段映射和来源追踪。

具体开发与部署另行确认，本文件不代表开始实施。

### 验收标准

- 源任务扫描进度与 ARTEX 同步状态清晰区分，源任务显示 `100%` 时不自动认定同步成功。
- 同步结果在刷新、离开页面并重新进入后仍可查看，并能定位到具体同步任务和时间。
- 成功、部分成功、失败的提示与实际结果一致；有失败项或未完成的数据时，不显示全部成功。
- 拉取、新增、更新、跳过、失败的统计口径有明确说明；重复同步不会被误认为新增了相同数量的资产。
- 缺少关键字段、解析失败、入库失败、关联 IP 写入失败均有可查询的原因，不再静默遗漏。
- 达到保护上限时，能够区分恰好达到上限与确实仍有数据未同步，并说明是否可以继续。
- 大批量同步中断后可继续处理，重试不会重复创建同一资产。
- 已同步资产可以追溯到源任务和源资产；字段映射及未同步信息有明确说明。

### 实施前待核实

- ScopeSentry 接口是否提供可靠的总数、稳定资产标识，以及稳定的分页或游标机制。
- 源任务名称变化时的关联方式，避免仅按名称追踪导致历史来源失效。
- 新增、更新、重复、跳过的判定规则，以及多任务引用同一资产时的去重和统计方式。
- 原始 JSON 与大体积附件的保存范围、展示方式和保留周期。

## Planner 提前收官与 Worker 收尾

- 记录日期：2026-10-10
- 状态：分析完成，待实施
- 问题来源：[任务 6](http://10.10.178.70:8787/function/tasks/detail/?id=6) 的运行记录及相关 Go 代码。
- 当前范围：记录分析与改进规划，本次不修改运行逻辑。
- 核心问题：系统把“Planner 认为证据足够”直接当成了“剩余工作都可以放弃”。
- 目标：让任务完成建立在原始目标和剩余工作评估之上，并在提交终态前保存 Worker 已有结果与未完成项。

### 已确认的现象

1. 任务 6 的目标是全面安全审计。Planner 第 39 轮仍认为存在独立的未测试方向，派出了 WebSocket 检查意图 `#2487` 和时序分析意图 `#2488`。
2. 第 40 轮拿到另一个 Worker 的会话测试结果后，Planner 调用 `prove_goal`，宣布目标达成、全面审计完成。
3. 系统随即将任务置为 `done`，取消两个仍在执行的 Worker。时序分析 `#2488` 的终态为 `aborted_streaming`，原因为 `goal_met`，底层错误为 `context canceled`，已运行 4 轮、约 1m43s；WebSocket 检查 `#2487` 则在工具执行阶段被取消。
4. `#2488` 最后一次 Bash 虽然显示正常返回，展开输出实际包含 Python `SyntaxError`，时序测试没有成功完成。取消使其无法继续修正脚本并形成结论；现有记录不能证明已经丢失了完成的漏洞结果。
5. `goal_met` 在中断信息中表示收官取消原因。将这些意图标记为 `stopped` 有助于区分主动停止与执行失败，但不能据此认定检查完成或不存在漏洞。

### 代码原因与评价

- [目标证明工具](../agent/tools.go)中的 `proveGoal` 校验证据节点类型及范围，随后标记目标达成；所有目标都为 `met` 后便返回完成。它没有独立校验剩余意图是否仍属于必要范围，也没有判断证据是否足以支撑全面完成。
- [任务引擎](../server/engine.go)收到 Planner 完成信号后，先写入 `done`，再通过 `AbortGoalMet` 取消任务上下文。这条路径没有等待 Worker 收尾。
- [执行框架](../norma/harness/query.go)在父上下文取消时退出；该取消路径不会进入预算耗尽时使用的结果补写阶段。
- [Worker](../agent/worker.go)已有收尾提示和结果补写能力；[超时收尾流程](../server/engine_timeout.go)也已有停止领任务、等待在途工作及最终 Planner 收尾的机制，可以作为设计参考。
- 当前 [Planner 提示](../agent/planner.go)对全面审计的收官已有约束，但提示仍依赖模型遵守，不能替代服务端状态校验。此次线上运行是否使用同一版提示，需要实施前核实。

评价：目标达成后停止重复或无关工作是合理的；对全面审计，仅凭一次达成判定立即取消仍有必要的独立检查，属于过于激进的提前收官。已经落库的事实和工具记录不会因此全部消失，风险主要在于必要检查尚未完成、已有输出尚未形成结论，以及最终报告掩盖未完成范围。

### 实施顺序

1. 核实线上版本、任务目标模型和相关状态转换，明确单点目标与全面审计各自的收官条件，并为关键取消场景建立回归验证。
2. 优先实现 WC-01 至 WC-03：先阻止不充分的收官，再接入限时收尾与最终复核，确保状态转换和结果保存一致。
3. 实现 WC-04，补齐页面和报告中的停止理由及未完成项，并验证全过程可追溯。

开发时按职责组织 Go 文件；若需要拆分现有大文件，先做保持行为不变的结构调整，再单独修改收官逻辑，便于分别验证和评审。

### 验收标准

- 重现任务 6 的场景：会话测试完成后，仍有必要的 WebSocket 或时序检查在执行时，不能仅凭该会话证据宣布全面审计完成。
- 单点或定量目标确已达成时，可以停止经评估为重复或无关的工作，并记录理由；不强制等待所有意图自然结束。
- 确认可收官后不再领取新工作；Worker 能在限定时间内保存已有事实、整理输出和登记未完成项，收尾不产生新探测。
- 已有工具输出包含脚本错误时，最终结论明确该检查未成功完成，不能把工具正常返回当作测试成功。
- 最终复核和必要回写完成后才提交终态；收尾超时、流式输出取消、工具执行取消均有明确原因及可查询记录。
- 用户暂停、用户取消与收官并发时，结果回写和终态保持一致，不出现假运行状态或终态被迟到操作覆盖。
- 原始证据、已保存结果和未完成范围可追溯；最终报告不将主动停止的检查描述为已验证通过。
